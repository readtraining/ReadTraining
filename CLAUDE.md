# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

pnpm + Turbo monorepo. Run these from the repo root:

```bash
pnpm install
pnpm dev          # api (4000) + web (3000)
pnpm dev:api      # builds packages/db, then Express + tRPC at http://localhost:4000/api/trpc
pnpm dev:web      # Next.js only, http://localhost:3000
pnpm build
pnpm typecheck    # tsc --noEmit in every package (the only static check)

pnpm db:generate  # after editing packages/db/src/schema.ts, writes SQL to packages/db/migrations (commit it)
pnpm db:migrate   # apply migrations to Supabase
pnpm db:push      # push schema directly, no migration
pnpm db:studio

pnpm admin:bootstrap <email> [--resend]   # invite the FIRST super admin (no account needed); everyone else: Admin › Team › Invite
pnpm admin:grant <email> [--preset support|finance|--super|--revoke|--reset-two-step|--list]   # change an existing login's admin role
pnpm live <command>     # run a command against the live project (LIVE_* in .env), e.g. pnpm live db:migrate
```

The Supabase dashboard settings every project needs (auth, SMTP, email templates, redirect URLs) are listed in `supabase/README.md`; the email templates are in `supabase/templates/`.

To run a command in one package, use `pnpm --filter @readtraining/<api|web|db> <script>`. The repo has no lint or test scripts. `playwright-core` is a devDependency of web, and QA is done by driving a browser against the dev server.

Env: copy `.env.example` to `.env` at the repo root. The API loads it through `tsx --env-file-if-exists=../../.env`, and drizzle-kit loads it through dotenv. `DATABASE_URL` is the Supabase transaction pooler (6543) and is used at runtime. `DIRECT_URL` (5432) is used for migrations. The web app reads the same root `.env` through `loadEnvConfig` in `next.config.ts` and inlines `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (the edge `proxy.js` can't read the root file).

Deploy: one Vercel project (`vercel.json`, Vercel Services). `/api/*` goes to the API service and everything else to the web app. Health check: `/api/trpc/health`.

## Architecture

- **packages/db**: Drizzle schema plus `createDb(url)`. It uses `prepare: false`, which the Supabase transaction pooler requires, and `max_pipeline: 0` (one query per connection at a time: the pooler hangs or mixes up answers when queries are pipelined, supabase/supavisor#1239). That setting needs `patches/postgres@3.4.9.patch` (listed in `pnpm-workspace.yaml`) so transactions still work; upgrading postgres.js means redoing or dropping the patch. It also re-exports `drizzle-orm`, so import operators like `eq` and `desc` from `@readtraining/db`. Types come from `src/index.ts`, but the runtime export is `dist/index.js`, so the package has to be built (`dev:api` does it) after schema or source changes.
- **apps/api**: ESM TypeScript with `.mts` files. Relative imports use `.mjs` extensions. The package exports `src/trpc/index.mts` (the `AppRouter` type). `src/trpc/trpc.mts` defines `createTRPCRouter`, `publicProcedure` and `protectedProcedure` (superjson transformer, zod errors flattened into `data.zodError`). The context (`src/trpc/context.mts`) holds `db`, the `user` from a verified Supabase access token (`Authorization: Bearer <access_token>`, checked by `verifyAccessToken` in `src/lib/supabase.mts`; none or an invalid one means signed out) and `loadIdentity()` (whether the session is still live, `isSessionLive`, and the person's roles, `loadActor` in `src/lib/actor.mts`, asked once per request). Feature routers go in `src/modules/<name>/<name>.router.mts` and are mounted in `src/trpc/router.mts`. Mounted routers: `health`, `me`, `organisations`, `catalogue`, `content`, `admin` (which holds the admin's own sub-routers) and `provider` (the provider workspace: `courses`, `cohorts`, `venues`, `profile`; every procedure is `orgProcedure(...)` on the caller's role). `src/lib/supabase.mts` is a server-only admin client (null when env is missing), and DB queries go through Drizzle.
- **apps/web**: Next.js 16 App Router, React 19. It is mostly `.jsx`; TS is used only for the tRPC client. It imports only the `AppRouter` **type** from `@readtraining/api` (`lib/trpc/react.ts`), so API code never enters the bundle. `app/layout.jsx` is a server component with the site-wide metadata; `app/Providers.jsx` (client) holds `TRPCProvider`, the cart `Context` (`context/Context.js`, persisted to localStorage under `rt-cart`) and the AOS animations. `app/sitemap.js`, `app/robots.js`, `app/error.jsx` and `app/global-error.jsx` exist. Path alias `@/*` → `apps/web/*`.

### The web app is built on the "Educrat" template

- The template's demo pages (`app/template/**`) and its unused components and data were deleted on 3 November 2026: every route is a real ReadTraining page, and `/template/...` addresses return 404 (except the few old ones that 308-redirect to their real page in `next.config.ts`). A few template parts the real site uses stay (`components/layout`, `components/others`, `components/common`, and the template's compiled CSS). The course listing is `/courses` (`components/courses/CourseCatalogue.jsx`), the subject/method pages `/courses/[slug]`, and course detail `/course/[slug]` (`components/courseDetail/*`; a numeric id redirects to the slug). Shop routes and auth routes are constants in `lib/routes.js`.
- **The public catalogue is real (Milestone 2).** The search page, the category/method/town pages (`lib/coursePages.js`), the course page, the basket's suggestions and the provider directory and profiles read the API: `catalogue.listings` / `catalogue.course` / `catalogue.locate` (`apps/api/src/modules/catalogue/listings.mts`) and `organisations.providerDirectory` / `.providerProfile`, through `lib/catalogueServer.js` and `lib/publicProvider.js` (server, cached a minute under the tag `courses`; an admin decision refreshes it at once, `app/admin/actions.js` `refreshCourses`). `lib/catalogueData.js` turns them into the shapes the pages read (`toCatalogueCourse`, `toCourseDetail`); nothing a course doesn't have (ratings, reviews, learner numbers) is shown or made up. A listing is a live shared page with at least one live provider course on it, or a provider course with its own page. A provider course can only go on a shared page for the same course: the same sub-category, and the same topic when both have one (`sameSubject` in `modules/provider/courses.mts`, `pagesForSubject` in `lib/taxonomy.js`). The course page never names providers (Hurak's way): it shows how many run the course, and the visitor picks a place, a date and a price. The search's filters, sorting and URL state are `lib/catalogueFilters.js`; `lib/courses.js` holds only shared helpers (`toCourseCard`, labels, formatters). **There are no fixed course numbers in the site's data:** a marketing or help page (licences, test prep, Security Jobs, blog, the HS&E test, the home page's built-in featured tabs) picks its courses by catalogue topic (`data/courseTopics.js` `TOPICS`, "category/sub-category/topic"; `lib/catalogueServer.js` `courseCards(picks)`), and a menu or button about a kind of course opens the course search (`courseSearch(words)`). A course's free mock test is matched by topic too (`data/testPrep.js` `mockTestCourses`). The learner, business and admin demo records use their own small demo list (`data/demoCourses.js`), never the public catalogue. Dev and test databases get sample courses from `pnpm --filter @readtraining/api seed:courses` (`--remove` takes them out). Live refuses it, except `pnpm live --filter @readtraining/api seed:courses --live-review`: the ten popular courses added for the client's review on 27 October 2026, to be removed (`--remove`) before a public launch. Test providers and courses made while trying live out are removed with `pnpm live --filter @readtraining/api remove:test-content` (it lists the candidates; `--provider <slug>` / `--course <slug>` show what would go; `--confirm` removes it; anything with an order or payout is refused). The provider directory (and so the sitemap) lists only providers with a live course. **The navigation is the live catalogue's too:** the header's Explore and Location menus, the mobile menu, the footer's course columns, the home page's subject tiles, search, course finder and team form read `catalogue.nav` (the active subjects with live courses, the methods in use, the towns of real venues and the live courses), loaded once on the server (`lib/catalogueServer.js` `loadNav`, addresses from `lib/nav.js` `withLinks`) and handed to the browser (`lib/navContext.js` `useNav`). A subject added in Catalogue settings shows up once it has a live course; a retired or empty one goes; no menu link leads to an empty search. The licence and help links stay fixed pages (`data/headerNav.js`). **Public forms never fake a result.** Every public form (checkout, contact, quotes, Security Jobs, HS&E test booking, licence help, certificate checker, newsletter, mock-test reviews and comments) has one switch in `apps/web/lib/forms.js` and is shown through `<FormGate form="…">` (`components/forms/FormGate.jsx`): while its `send` is `null` the site shows the shared "coming soon" panel with the real phone and email (or nothing, for hidden ones); put the real server call there and the form appears everywhere it is used. A reference only ever comes from the server. `pnpm check:forms` (run in CI) fails on a made-up reference, a simulated send or a public form outside `FormGate`.
- Course detail page: `BookingProvider` holds the selected mode, session and quantity, and syncs it to URL query params (e.g. `?mode=inhouse`, `?dates=open`). The booking card, mobile buy bar and sections read from it. Team/group wording lives only in `lib/teamTraining.js`, so all surfaces show the same text. Analytics events go through `lib/analytics.js` (`trackEvent`, GA4 dataLayer).
- Styling uses Bootstrap plus the template's compiled CSS (`public/assets/css/main.css`), imported by `public/assets/sass/styles.scss`. All ReadTraining styling goes in `public/assets/sass/custom.scss` with `rt-` prefixed BEM-ish classes (`rt-cd__*` for course detail, `rt-home`, `rt-card`, etc.). Don't edit the template CSS. **New pages and components follow `apps/web/DESIGN-SYSTEM.md`** (tokens in the `DESIGN TOKENS` block of custom.scss): no hex values, one type scale per page type, the shared layout parts and `.rt-field` forms.
- Copy is UK English (`lang="en-GB"`, GBP).

### Accounts, provider workspace and admin

- **Auth is Supabase Auth in the web app**, not the API: `lib/supabase/{client,server}.js`, `lib/auth/*`, and `proxy.js` (Next 16's name for middleware). The proxy refreshes the session cookie, sends signed-out visitors of `/account`, `/business` and `/provider` to `/login?next=…`, and sends signed-in visitors away from `/login` and `/signup`. It also sends `/courses?subject=<one subject>` to that subject's page `/courses/<subject>` (308, other filters kept), so each subject has one address; links use the page form. Pages still check the session themselves. With no Supabase env, protected areas redirect to login and the rest of the site works.
- `/account` (learner), `/business` (business account) and `/provider/*` (provider workspace, modelled on Hurak's provider side; `lib/providerWorkspace.js`) are mostly front end only: their records are demo data in `data/` plus localStorage. Their real parts are the account's settings, the organisations, a provider's account status (a one-line status bar on every workspace page, `ProviderAccountStatus`; the Account review page `/provider/review` with our team's message, "send for review" and the history from `activity_log`; the dashboard's getting-set-up checklist, `ProviderChecklist`; the name can change only while the account is under review) and, since Milestone 2, the provider's courses (editor, images, approval, changes to a live course waiting in `course_revisions`), dates (`cohorts`), venues, profile, logo and terms, all through the API `provider.*` (images and logos in the public `course-media` bucket, uploaded through signed addresses). The browser hides buttons with the shared table (`lib/providerAccess.js`). Orders, learners, bookings, reviews, leads, price plans and the sample cohorts they link to are still demo (`lib/providerWorkspace.js`); a cohort page with a non-uuid id is a sample one. `/admin/*` (operator panel) is part real, part demo (Part B of `docs/milestone-1-and-admin.md`):
  - **Real (API `admin.*`, `content.*`):** admin team, activity log, learners, providers and approvals (decisions email the owner), commission, catalogue settings (categories, methods, levels), site content, emails (every automated email's words: `apps/api/src/emails/templates.mts`, saved as content keys `email:<template>`, never sent to the website; the "something is waiting" emails (a provider application or course received, a new business account, an admin's access changed, and the alerts to every admin with the `approve` switch) go through `apps/api/src/lib/notify.mts`, after the change is saved, and never block it), coupons (`coupons` table), course approvals and the catalogue's courses (`admin.courses` in `modules/admin/courses.mts`: new courses and changes to live courses, decisions emailed to the provider's owner, and the shared course pages staff write and publish in the provider course editor run with `scope="admin"` through `lib/courseEditorApi.js`), money (orders, refunds, disputes, payouts and the append-only `ledger_entries`, in `modules/admin/money.mts` and `payouts.mts`; the maths is `apps/api/src/lib/money.mts`: fee off the gross, commission on the net, amounts in pence; no payment provider yet, so orders come from staff bookings and refunds/payouts are recorded, not paid; `pnpm --filter @readtraining/api seed:money` adds made-up records to a dev database, never live) and platform settings (the search-engine words, content key `seo`, and which outside services' environment variables are set; their values never leave the server). Each has its own router in `apps/api/src/modules/admin/` (and `modules/content/`), checks one switch with `adminProcedure(...)`, and writes `activity_log`.
  - **Still demo:** sessions, change requests, requests, businesses, Security Jobs, certificates, reports, reviews (`lib/adminReviews.js`) and the fees preview. Demo pages say so beside their title (the nav's `demo` in `data/admin.js`; `AccountShell`'s `demo` for the learner and business accounts). These go through `lib/adminStore.js` (one `rt-admin` record and an `rt-admin-change` event), which `lib/admin.js` and `lib/adminWork.js` build on; they are the seam to swap for API calls.
  - **Site content** (admin > Site content) is the editable part of the public site: the trust numbers, the home page's featured courses, testimonials, the video words, each page's FAQs and the legal pages. The key/value rows are `site_content` (every save is also kept in the append-only `site_content_versions`). The website reads them through `lib/siteContent.js` (`await loadSiteContent()` from `lib/siteContentServer.js` first, on the server): a key never saved uses the built-in wording in `data/`, so the site reads the same until an admin changes something. A page's FAQ is `faqItems(key, builtInItems)` and must also be listed in `data/faqSets.js`; the legal pages read through `lib/legal.js`; the browser only receives the trust numbers (`browserContent`). A change marks the saved copy out of date (`app/admin/actions.js`, `updateTag`), and the root layout's `revalidate = 300` makes prebuilt pages catch up within 5 minutes. Never retype a number the trust numbers hold; use `trustFigures()`. The trust numbers have built-in values only where they can be proved (UK law bans unverifiable review claims): the rating and number of reviews count every one of our reviews (4.9 from 1,160, Read Training's Google listing, checked 2 November 2026), with an optional `source` (shown beside the rating as text) and `sourceUrl` (kept as a record, not shown) (built in: Google and the listing; an admin can clear them); customers and courses are null until an admin enters them, and every page leaves a null one out, and an FAQ quoting it (`{customers}`...) is left out too. There are no built-in testimonials and no video story (the old ones were copied from Hurak).
- **Customer reviews** are their own table, `reviews` (admin › Customer reviews, `modules/admin/reviews.mts`; the site reads `content.reviews` through `lib/siteReviewsServer.js`, tag `reviews`, helpers in `lib/siteReviews.js`). `source` is `imported` (a real customer's review copied word for word from another site, with `origin`/`origin_url` when known; the source shows on the card as text, not a link, and the link is kept as a record) or `booking` (a later milestone: `order_id`, unique, with `course_id` and `provider_id` from the order, starting `pending`, with an optional provider reply). Any rating from 1 to 5 is kept: refusing a low one would be suppressing negative reviews (DMCC Act 2024). The website shows the published ones and says it shows a selection, and that the overall rating counts every review. `review_date` is null when the real day isn't known (never worked out from "3 weeks ago"; `date_is_approximate` marks a close one). A review names a course topic only when its text clearly names the course. A course page shows the published reviews that name its topic, under "Reviews of Read Training" (it lists several providers' dates, so it says whose reviews they are), with a link to /customer-reviews?course=<topic name>; booking reviews of a course (`course_id`) come later. Up to 4 go on the home page. With none published, the home section is left out and /customer-reviews shows an empty state (noindex, out of the sitemap and the footer). `pnpm --filter @readtraining/api seed:reviews` adds the imported ones: five from Google and the 198 5-star reviews Trustpilot showed publicly on 2 November 2026 (`apps/api/src/scripts/data/trustpilot-reviews.json`, each with its own date, "Trustpilot" as its source and its link there; Trustpilot shows only the latest 200 of a filter without signing in, so older ones need the client's Trustpilot business export). `--remove` takes them out; live needs `--live`, only after asking. /customer-reviews shows them 12 at a time with "Show more reviews".

## Database rules (Supabase + Drizzle)

The schema is built on a development Supabase project and replayed later on the client's test and live projects, so the migrations must rebuild everything from an empty database.

- Every change goes `packages/db/src/schema.ts` → `pnpm db:generate` → `pnpm db:migrate`. Never change tables in the Supabase dashboard, and never use `db:push` on a shared or client database.
- Never edit a migration that has already run. A fix is always a new migration.
- Supabase-specific SQL (triggers on `auth.users`, RLS policies, grants, storage buckets, extensions) goes in custom migrations (`drizzle-kit generate --custom --name <name>`), not in the dashboard.
- No demo or test data in migrations. Seed data goes in a separate script that never runs on live.
- Every public table calls `.enableRLS()`. Drizzle connects as `postgres` and skips RLS, but the Data API is reachable with the public key, so RLS is what protects it. Policies are owner-only reads using `(select auth.uid())`; writes go through the API.
- Database functions are `security definer` with `set search_path = ''`.
- Append-only tables (`activity_log`, `site_content_versions`, `ledger_entries`) have no foreign keys, so removing an account never has to change a row, and a trigger blocks update, delete and truncate.
- Run the Supabase security and performance advisors after each migration. Before moving to the client, apply all migrations to a fresh, empty project first.

## Sign-in and security rules

- On the server, verify the user with `supabase.auth.getClaims()` (it checks the JWT signature locally), never `getSession()`. Use `getUser()` only when fresh user data is needed.
- Only the publishable key reaches the browser. The service-role key stays in the API, for admin tasks only.
- Email links (confirm, reset) use the token-hash flow at `/auth/confirm`. Google/Facebook use `/auth/callback` (PKCE code exchange).
- A `next` redirect is accepted only if it starts with `/` and not `//`.
- Forgot password always shows the same message, so it never reveals whether an email exists.
- Changing email or password requires the current password.
- The tRPC client sends `Authorization: Bearer <access_token>`, and the API verifies it with `getClaims(token)` (issuer, audience and role checked). A protected call also needs the session to still exist and the account not to be banned or deleted (`isSessionLive`), since a token stays valid until it expires.

## Identities, roles and permissions

One login can hold several identities:
- Student: every account.
- Business and Provider: an `organisations` row with `organisation_members`.
- Admin: an `admin_users` row, signed in at `/admin/login`, with no public sign-up. Admins are invited (`apps/api/src/lib/adminInvite.mts`): someone without an account gets a staff-only login (`admin_only`, kept out of Learners) and an email to `/admin/welcome` to set their name and password; access starts only when the invite is accepted.

Roles:
- Provider roles follow Hurak: owner, admin, tutor, course_editor, support, sales, accounts, marketing, assistant.
- Business roles: owner, member.
- Admins have one role with permission switches and presets (Full, Support, Finance). Full requires two-step sign-in (`needsTwoStep`; a Full admin without an authenticator sets one up at the admin login). A test copy can waive it for a client review with `ADMIN_TWO_STEP_OPTIONAL=1`, which live ignores (`apps/api/src/lib/actor.mts`).

How permissions are checked:
- One shared `can(actor, action, target)` table, used by both the API and the web server code.
- It is enforced on the server: in tRPC procedures (signed in, organisation member, admin permission) and in the server layouts for `/provider`, `/business` and `/admin`. The browser uses it only to hide buttons.
- Provider staff only ever see their own organisation's data. Within it, the organisation's private details (its mobile, commission, terms acceptance and our team's status note and messages) are for the owner and admins only: the database policy "organisations: read where owner or admin" (migration 0025) and the API (`PRIVATE_ROLES` in `modules/provider/profile.mts`, used by `profile.review` and `organisations.openWorkspace`); other members see the account's status without the note.
- Every allowed change and every refused attempt is written to `activity_log`, which is append-only (no update or delete).
- Course review: a provider's change to a course waiting for approval (words or pictures) takes it out of review, back to a draft (`leaveReview` in `modules/provider/courses.mts`), so admins never approve an unseen version; approval re-checks `missing()`; a change to a live course is decided on the version the admin saw (`seen`, the change's time) and one edited since is refused. "Own request" for courses = whoever created or last sent the course, or anyone who worked on the change (from `activity_log`). A course number (`/course/1012`) opens only public courses. A course never goes live under a retired category, sub-category, topic, method or level: retiring one with live courses filed under it is refused (`modules/admin/catalogue.mts`), and every step that puts a course live (approve, approve a change, resume, publish a shared page, a provider un-pausing) checks it (`lib/retired.mts`). Two people (or two tabs) editing one course: the editor sends the version its draft was loaded from (`seen`; the version is the later of `updated_at` and a waiting change's time, `courseVersion` in `modules/provider/courses.mts`), and `provider.courses.update` / `admin.courses.updateShared` refuse a save over a newer one ("changed somewhere else… load the latest version"); the editor's own actions return the new version (`lib/courseEditorApi.js`). A live or paused course keeps at least one image. A course image is at least 500 × 300 pixels: the editor checks the chosen file, and `addCourseImage` reads the stored file's size (`imageSize` in `lib/media.mts`) and deletes one that is smaller or unreadable.
- Nobody decides on their own request (`notOwnRequest`). One exception, for approvals only (a provider account, a course or a change to one; never payouts or refunds): a Full admin may decide on their own request when no other active admin has the approve switch, with a written reason; it is logged as `admin.own_request_decided` (`apps/api/src/lib/soleApprover.mts`). It switches itself off once a second approver exists.
