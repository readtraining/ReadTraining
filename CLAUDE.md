# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

pnpm + Turbo monorepo. Run these from the repo root:

```bash
pnpm install
pnpm dev          # api (4000) + web (3000)
pnpm dev:api      # builds packages/db, then Express + tRPC at http://localhost:4000/api/trpc
pnpm dev:web      # Next.js only, http://localhost:3000
pnpm build
pnpm typecheck    # tsc --noEmit in every package (the only static check)

pnpm db:generate  # after editing packages/db/src/schema.ts, writes SQL to packages/db/migrations (commit it)
pnpm db:migrate   # apply migrations to Supabase
pnpm db:push      # push schema directly, no migration
pnpm db:studio

pnpm admin:bootstrap <email> [--resend]   # invite the FIRST super admin (no account needed); everyone else: Admin › Team › Invite
pnpm admin:grant <email> [--preset support|finance|--super|--revoke|--reset-two-step|--list]   # change an existing login's admin role
pnpm live <command>     # run a command against the live project (LIVE_* in .env), e.g. pnpm live db:migrate
pnpm --filter @readtraining/api cleanup:media [--confirm]   # course pictures and logos uploaded but never attached (over a day old); lists them, deletes with --confirm
```

The Supabase dashboard settings every project needs (auth, SMTP, email templates, redirect URLs) are listed in `supabase/README.md`; the email templates are in `supabase/templates/`.

To run a command in one package, use `pnpm --filter @readtraining/<api|web|db> <script>`. The repo has no lint or test scripts. `playwright-core` is a devDependency of web, and QA is done by driving a browser against the dev server.

Env: copy `.env.example` to `.env` at the repo root. The API loads it through `tsx --env-file-if-exists=../../.env`, and drizzle-kit loads it through dotenv. `DATABASE_URL` is the Supabase transaction pooler (6543) and is used at runtime. `DIRECT_URL` (5432) is used for migrations. The web app reads the same root `.env` through `loadEnvConfig` in `next.config.ts` and inlines `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (the edge `proxy.js` can't read the root file).

Security headers: every page gets a Content-Security-Policy, HSTS, X-Content-Type-Options, Referrer-Policy, X-Frame-Options and Permissions-Policy (`next.config.ts` `SECURITY_HEADERS`), and the API's answers get their own (`apps/api/src/index.mts`). Before using a new outside service in the browser (a script, frame, image host or API), add its origin to the CSP there, or the browser blocks it.

Deploy: one Vercel project (`vercel.json`, Vercel Services). `/api/*` goes to the API service and everything else to the web app. Health check: `/api/trpc/health`.

## Architecture

- **packages/db**: Drizzle schema plus `createDb(url)`. It uses `prepare: false`, which the Supabase transaction pooler requires, and `max_pipeline: 0` (one query per connection at a time: the pooler hangs or mixes up answers when queries are pipelined, supabase/supavisor#1239). That setting needs `patches/postgres@3.4.9.patch` (listed in `pnpm-workspace.yaml`) so transactions still work; upgrading postgres.js means redoing or dropping the patch. It also re-exports `drizzle-orm`, so import operators like `eq` and `desc` from `@readtraining/db`. Types come from `src/index.ts`, but the runtime export is `dist/index.js`, so the package has to be built (`dev:api` does it) after schema or source changes.
- **apps/api**: ESM TypeScript with `.mts` files. Relative imports use `.mjs` extensions. The package exports `src/trpc/index.mts` (the `AppRouter` type). `src/trpc/trpc.mts` defines `createTRPCRouter`, `publicProcedure` and `protectedProcedure` (superjson transformer, zod errors flattened into `data.zodError`). The context (`src/trpc/context.mts`) holds `db`, the `user` from a verified Supabase access token (`Authorization: Bearer <access_token>`, checked by `verifyAccessToken` in `src/lib/supabase.mts`; none or an invalid one means signed out) and `loadIdentity()` (whether the session is still live, `isSessionLive`, and the person's roles, `loadActor` in `src/lib/actor.mts`, asked once per request). Feature routers go in `src/modules/<name>/<name>.router.mts` and are mounted in `src/trpc/router.mts`. Mounted routers: `health`, `me`, `organisations`, `catalogue`, `content`, `admin` (which holds the admin's own sub-routers) and `provider` (the provider workspace: `courses`, `cohorts`, `venues`, `profile`; every procedure is `orgProcedure(...)` on the caller's role). `src/lib/supabase.mts` is a server-only admin client (null when env is missing), and DB queries go through Drizzle.
- **apps/web**: Next.js 16 App Router, React 19. It is mostly `.jsx`; TS is used only for the tRPC client. It imports only the `AppRouter` **type** from `@readtraining/api` (`lib/trpc/react.ts`), so API code never enters the bundle. `app/layout.jsx` is a server component with the site-wide metadata; `app/Providers.jsx` (client) holds `TRPCProvider`, the cart `Context` (`context/Context.js`, persisted to localStorage under `rt-cart`) and the AOS animations. `app/sitemap.js`, `app/robots.js`, `app/error.jsx` and `app/global-error.jsx` exist. Path alias `@/*` → `apps/web/*`.

### The web app is built on the "Educrat" template

A listing is a live shared page with at least one live provider course on it, or a provider course with its own page. A provider course goes on the shared page for its own subject automatically (`placeOn`): the same sub-category, and the same topic when both have one (`sameSubject` in `modules/provider/courses.mts`, `pagesForSubject` in `lib/taxonomy.js`). The course page never names providers: it shows how many run the course, and the visitor picks a place, a date and a price. The search's filters, sorting and URL state are `lib/catalogueFilters.js`; `lib/courses.js` holds only shared helpers (`toCourseCard`, labels, formatters). **There are no fixed course numbers in the site's data:** a marketing or help page (licences, test prep, Security Jobs, blog, the HS&E test, the home page's built-in featured tabs) picks its courses by catalogue topic (`data/courseTopics.js` `TOPICS`, "category/sub-category/topic"; `lib/catalogueServer.js` `courseCards(picks)`), and a menu or button about a kind of course opens the course search (`courseSearch(words)`). A page built from fixed wording checks such a link against the live catalogue on the server (`searchFinds`, `liveLinks`, `liveHref` in `lib/catalogueServer.js`): one that would find nothing is left out (Security Jobs), becomes "Ask about … training" (a licence guide's Book button) or opens all courses (test prep), so no link lands on "No courses match". A course's free mock test is matched by topic too (`data/testPrep.js` `mockTestCourses`). The learner, business and admin demo records use their own small demo list (`data/demoCourses.js`), never the public catalogue. Dev and test databases get sample courses from `pnpm --filter @readtraining/api seed:courses` (`--remove` takes them out). Live refuses it, except `pnpm live --filter @readtraining/api seed:courses --live-review`: the ten popular courses added for the client's review on 27 October 2026, to be removed (`--remove`) before a public launch. `--remove` takes out only the sample providers and their courses, dates, venues and pictures: the shared course pages are ReadTraining's own (SIA Door Supervisor has the client's words) and stay, hidden until a real provider lists a course on one. Test providers and courses made while trying live out are removed with `pnpm live --filter @readtraining/api remove:test-content` (it lists the candidates and flags a name saying test or sample, two providers with one name, a course with its shared page's words copied and a venue whose town isn't in the UK or near its postcode; `--provider <slug>` / `--course <slug>` show what would go; `--confirm` removes it; anything with an order or payout is refused). The provider directory (and so the sitemap) lists only providers with a live course. **The navigation is the live catalogue's too:** the header's Explore and Location menus, the mobile menu, the footer's course columns, the home page's subject tiles, search, course finder and team form read `catalogue.nav` (the active subjects with live courses, the methods in use, the towns of real venues and the live courses), loaded once on the server (`lib/catalogueServer.js` `loadNav`, addresses from `lib/nav.js` `withLinks`) and handed to the browser (`lib/navContext.js` `useNav`). A subject added in Catalogue settings shows up once it has a live course; a retired or empty one goes; no menu link leads to an empty search. The licence and help links stay fixed pages (`data/headerNav.js`). **Public forms never fake a result.** Every public form (checkout, contact, quotes, Security Jobs, HS&E test booking, licence help, certificate checker, newsletter, mock-test reviews and comments) has one switch in `apps/web/lib/forms.js` and is shown through `<FormGate form="…">` (`components/forms/FormGate.jsx`): while its `send` is `null` the site shows the shared "coming soon" panel with the real phone and email (or nothing, for hidden ones); put the real server call there and the form appears everywhere it is used. A reference only ever comes from the server. `pnpm check:forms` (run in CI) fails on a made-up reference, a simulated send or a public form outside `FormGate`.

### Accounts, provider workspace and admin

- **Auth is Supabase Auth in the web app**, not the API: `lib/supabase/{client,server}.js`, `lib/auth/*`, and `proxy.js` (Next 16's name for middleware). The proxy refreshes the session cookie, sends signed-out visitors of `/account`, `/business` and `/provider` to `/login?next=…`, and sends signed-in visitors away from `/login` and `/signup`. It also sends `/courses?subject=<one subject>` to that subject's page `/courses/<subject>` (307, so a subject retired later isn't kept by browsers; other filters kept), so each subject has one address; links use the page form. Pages still check the session themselves. With no Supabase env, protected areas redirect to login and the rest of the site works.
- **Learning options:** one provider course can be offered several ways with one set of words, pictures, syllabus and FAQs. `courses.methods` holds the options it is offered (classroom, live-online, self-paced; database checks `courses_methods_taught`, `courses_method_offered`) and `courses.method` the primary one, one of them, shown first everywhere (`waysOf` / `waysLabel` in `lib/courseModes.js`; on the course page `primaryMode` picks the mode the booking card opens on). A shared page has neither. Set in the editor's Learning options step (`ModeSection`: the primary as cards, the others as switches; `setLearningOptions` in `modules/provider/courses.mts`), not reviewed (like prices). A dated option with upcoming dates can't be turned off until they are cancelled (checked under the course's row lock; creating a date locks the same row and checks its `method` is one of the course's dated options, `provider.cohorts.create`); a date keeps its own `method`. Only the self-paced option has a course price or plan (`price_pence`, `plan_id`): turning it off clears them, and a live course turning it on needs one. A new option or primary must be active in Catalogue settings; a retired one can be turned off but not on, and a method can't be retired while live courses offer it (`filedUnder` in `modules/admin/catalogue.mts`). Listings and the provider's public courses list a course under every option. **Stop new bookings**: `courses.closed_methods` holds the options not taking bookings; they stay in `methods`, never the primary, and one option always stays open (checks `courses_closed_methods_*`, migration 0038). `provider.courses.setOptionOpen` (the Learning options step's Taking bookings card, under the row lock with `seen`, logged `course.option_stopped` / `course.option_reopened`, not reviewed) stops or reopens one; stopping the primary makes the first open option the primary, and stopping the last open one is refused (pause the course instead). Dates are never rewritten: a date is on sale only while its own `bookable` is on and its method isn't closed, so the catalogue, the course page, the provider directory, new dates (`provider.cohorts.create`) and staff bookings all leave a closed option out, and "Take bookings again" restores it as it was. An option with upcoming dates can't be turned off (stop its bookings instead); a closed one with none can, and leaves `closed_methods` with it. A retired method that is only a closed option doesn't stop a course going live (`lib/retired.mts`), and can't be reopened.
- **Topics are chosen by our team, never the provider.** A provider files a course by category and sub-category only: the New course pop-up and the editor have no topic field for them (`access.topic` in `lib/courseEditorApi.js`: only ReadTraining's own editors, shared pages and staff, show it), `provider.courses.create` / `update` ignore one sent, and a provider moving a course to another sub-category clears it. Approving a course, or a change to one, whose sub-category has active topics needs one of them (`topic` on `admin.courses.decide`; `topicChoice` / `fileTopic` in `modules/admin/courses.mts`, under the course lock, before `placeBySubject`, so the course lands on the right shared page; logged in the decision's `metadata.topic`): always chosen for a new course, and for a change only when it moves the sub-category or the course has no topic (one that still fits is kept). The admin's course page and Approvals ask in the Approve pop-up (`TopicField` in `AdminCourse.jsx`); such courses aren't ticked for "Approve selected". A sub-category without topics needs none and keeps none. Staff moving a live course's sub-category choose its topic too. There is no "suggest a sub-category": a provider picks the closest one, and our team asks for changes when it is wrong.
- **Closing an account** is a request, not a self-service delete: Account settings › Close your account (`me.requestClosure`, current password unless they sign in with Google; `me.withdrawClosure`) saves it in `account_closure_requests` (API only, no foreign key, so the record outlives the account; one open request per person), logs `account.closure_requested`, emails the person (`closure-received`) and every admin with the `suspend` switch (`admin-closure-request`, `notifyAdmins` in `lib/notify.mts`). Staff with the `suspend` switch carry it out in Admin › Closure requests (`admin.closures` in `modules/admin/closures.mts`; also a Close account button on the learner's page), nearest one-month deadline first (UK GDPR): closing deletes the login in the same transaction as the request is marked done (the profile, memberships and admin row cascade; orders and money records stay with the login link set to null; the request keeps the email as the record and drops the reason), then removes their photo file and emails them (`closure-done`). ## Database rules (Supabase + Drizzle)

The schema is built on a development Supabase project and replayed later on the client's test and live projects, so the migrations must rebuild everything from an empty database.

- Every change goes `packages/db/src/schema.ts` → `pnpm db:generate` → `pnpm db:migrate`. Never change tables in the Supabase dashboard, and never use `db:push` on a shared or client database.
- Never edit a migration that has already run. A fix is always a new migration.
- Supabase-specific SQL (triggers on `auth.users`, RLS policies, grants, storage buckets, extensions) goes in custom migrations (`drizzle-kit generate --custom --name <name>`), not in the dashboard.
- No demo or test data in migrations. Seed data goes in a separate script that never runs on live.
- Every public table calls `.enableRLS()`. Drizzle connects as `postgres` and skips RLS, but the Data API is reachable with the public key, so RLS is what protects it. Policies are owner-only reads using `(select auth.uid())`; writes go through the API. A table the browser doesn't read (all but `profiles`, `organisations`, `organisation_members`) has no grants for `anon` or `authenticated` and an explicit restrictive "<table>: API only" policy (migration 0025); new tables start with no grants. So a new API-only table needs that policy in a custom migration (or the Security Advisor flags it), and a table the browser must read needs `grant select ... to authenticated` plus an owner-only policy.
- Database functions are `security definer` with `set search_path = ''`.
- Append-only tables (`activity_log`, `site_content_versions`, `ledger_entries`) have no foreign keys, so removing an account never has to change a row, and a trigger blocks update, delete and truncate.
- An action that checks a row's state and then changes it locks the row first: inside the transaction, `select ... for update`, check again, then write (`lockCourse`/`lockStatus` in `modules/provider/courses.mts`, `lockTeam` in `modules/admin/team.mts`). Emails go after the commit. So two clicks or two people at the same moment act once, and the second is told it has been done.
- Run the Supabase security and performance advisors after each migration. Before moving to the client, apply all migrations to a fresh, empty project first.

## Sign-in and security rules

- **Bots and abuse (four layers).** (1) The Vercel Firewall (dashboard, free Hobby plan): known scanner paths are denied and
  each IP gets 300 `/api/` requests a minute. (2) Cloudflare Turnstile: `apps/web/lib/humanCheck.js` gets a fresh one-use token
  on sign-up, sign-in, forgot password, the confirmation resend and both admin sign-ins (passed to Supabase as `captchaToken`;
  Supabase's CAPTCHA protection checks it), and on every public form (`sendForm` adds `humanCheck`; the API's
  `publicFormProcedure` checks it with `lib/humanCheck.mts`, so every public form endpoint MUST be built on it). (3) The API:
  `lib/rateLimit.mts` (Upstash Redis via `KV_REST_API_*`, or memory without them) caps each IP at 300 requests a minute and,
  through `limit(ctx, name)`, provider applications, business accounts, admin invites and picture-upload links per person; a
  request body over 100 KB is refused (413). (4) The `course-media` bucket accepts only images up to 2 MB. Production needs
  `NEXT_PUBLIC_TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY`; preview and development copies use Cloudflare's test keys.
  Supabase's CAPTCHA switch is turned on only after the code that sends the token is live (otherwise nobody can sign in).

- On the server, verify the user with `supabase.auth.getClaims()` (it checks the JWT signature locally), never `getSession()`. Use `getUser()` only when fresh user data is needed.
- Only the publishable key reaches the browser. The service-role key stays in the API, for admin tasks only.
- Email links (confirm, reset) use the token-hash flow at `/auth/confirm`. Google/Facebook use `/auth/callback` (PKCE code exchange).
- A `next` redirect is accepted only if it starts with `/` and not `//`, checked again after `.` and `..` are tidied away (`/.//evil.com` becomes `//evil.com`), one rule for all: `lib/safeNext.js`.
- Forgot password always shows the same message, so it never reveals whether an email exists.
- Changing email or password requires the current password. Someone who signs in with Google or Facebook (no password) can add one in Account settings › Password (`me.setPassword`): only within 15 minutes of signing in (otherwise the page offers "Sign in with Google again"), logged as `account.password_set`, and they are emailed (`password-added`).
- The tRPC client sends `Authorization: Bearer <access_token>`, and the API verifies it with `getClaims(token)` (issuer, audience and role checked). A protected call also needs the session to still exist and the account not to be banned or deleted (`isSessionLive`), since a token stays valid until it expires.

## Identities, roles and permissions

One login can hold several identities:
- Student: every account. A learner is at least 16 (`MIN_AGE` in `modules/me/me.router.mts` and `AccountProfile.jsx`; the work courses here start at 16).
- Business and Provider: an `organisations` row with `organisation_members`.
- Admin: an `admin_users` row, signed in at `/admin/login`, with no public sign-up. A login that also has a provider account switches between the two in Switch account ("Admin panel" first, `useSwitchAccount`; only for an active admin whose invite is accepted and who has a provider account that isn't rejected): /admin still asks for the admin sign-in and two-step, and going back opens their own provider account with their own role, never as staff. Admins are invited (`apps/api/src/lib/adminInvite.mts`): someone without an account gets a staff-only login (`admin_only`, kept out of Learners) and an email to `/admin/welcome` to set their name and password; access starts only when the invite is accepted.

Roles:
- Provider roles: owner, admin, tutor, course_editor, support, sales, accounts, marketing, assistant.
- Business roles: owner, member.
- Admins have one role with permission switches and presets (Full, Support, Finance). Two-step sign-in is switched off for every admin while the platform is built and tested (`ADMIN_TWO_STEP = false` in `packages/permissions`): admins sign in with email and password only, an authenticator set up earlier isn't asked for, and the Team and learner pages don't show two-step. Set it back to true before launch: then a Full admin without an authenticator sets one up at the admin login, and any admin who has one is asked for it (`needsTwoStep`). A test copy can waive it for a client review with `ADMIN_TWO_STEP_OPTIONAL=1`, which live ignores (`apps/api/src/lib/actor.mts`).
- **Each admin sees only what they can work on.** Full: everything (the super admin alone also manages Full admins). Support: everything except refunds, wallet credit, payouts, adjustments, financial settings, the admin team and platform settings (`SUPPORT_EXCLUDES`). Finance: money only. A rule's `permission` in `ADMIN_RULES` is one switch or any of several; every admin read has its own area rule (`admin.courses.view`, `admin.providers.view`/`.read`, `admin.coupons.view`, `admin.emails.view`, `admin.content.view`…), the activity log shows a non-Full admin their own entries and their areas' (`seenBy` in `modules/admin/activity.mts`), and each menu page names the switches that open it (`permission` in `data/admin.js` nav): AdminShell lists only those, shows "You don't have access to this page" for the others (so demo pages' buttons are closed too), and the Dashboard, search and badges follow the same switches; a link to a page the admin can't open is plain text (`PageLink` in `adminParts.jsx`).

How permissions are checked:
- One shared `can(actor, action, target)` table, used by both the API and the web server code.
- It is enforced on the server: in tRPC procedures (signed in, organisation member, admin permission) and in the server layouts for `/provider`, `/business` and `/admin`. The browser uses it only to hide buttons.
- Provider staff only ever see their own organisation's data. Within it, the organisation's private details (its mobile, commission, terms acceptance and our team's status note and messages) are for the owner and admins only: the database policy "organisations: read where owner or admin", active members only (migration 0028) and the API (`PRIVATE_ROLES` in `modules/provider/profile.mts`, used by `profile.review` and `organisations.openWorkspace`); other members see the account's status without the note.
- Every allowed change and every refused attempt is written to `activity_log`, which is append-only (no update or delete). A change and its log line are written in one transaction. The IP recorded (`ctx.ip`, and the rate limits: `clientIp` in `lib/clientIp.mts`) trusts forwarded headers only on Vercel (or with `TRUST_PROXY=1`, then only the last x-forwarded-for entry); elsewhere it is the connection's address.
- Course review: a provider's change to a course waiting for approval (words, pictures, prices, learning options) keeps it in review as the new version: its `submitted_at` moves on (`keepInReview` in `modules/provider/courses.mts`, logged `course.edited_in_review`), so an admin who opened the earlier version is refused (`seen`) and admins never approve an unseen version, and whoever made the change counts as asking for the decision (`requesters` in `modules/admin/courses.mts`); search and privacy settings leave it as it was sent; it keeps its place in our team's queue, which goes by when it was sent (the activity log's `course.submitted`, `sent` in `admin.courses` approvals; `at`/`seen` stay the version); a save can't take away what it was sent with (a unit, outcomes, its last image, the self-paced price: refused, "withdraw it from review first"). Sending a course for approval, publishing a shared page and approving a course need a short description of at least 50 characters and a description of at least 200 (`MIN_TEXT` in `modules/provider/courses.mts`, the editor's `MIN`; a draft saves with less), and a date learners can book (not cancelled, taking bookings, starting after today) on each way it is taught on dates that is taking bookings (`datesMissing` in `modules/provider/courses.mts`, in `missing()`; the editor's Price step ticks by the same rule); once live, its dates may run out; approval re-checks `missing()`; a change to a live course is decided on the version the admin saw (`seen`, the change's time) and one edited since is refused. Deleting a provider's course (owner and admin roles only; the editor's gear, `provider.courses.remove`): a draft or a course our team asked to change is deleted after a simple confirmation; one waiting for review can't be (the gear offers Withdraw from review, `provider.courses.withdrawReview`, back to a draft, and an admin's decision on it is then refused: "The provider withdrew this course from review."); one that has been live (live or paused) is deleted only while nobody has booked or reviewed it (no `orders` or `reviews` row with its `course_id`), with its name typed (`confirmTitle`, checked by the API too), and the admins with the `approve` switch are emailed after the commit (`admin-course-deleted`); one our team has paused (`paused` with their reason in `status_note`; a course the provider paused has none) can't be deleted while it is paused (the gear shows the reason and Contact us, with no Delete or Put back live); one learners have booked or reviewed is paused instead. `deleteBlock` in `modules/provider/courses.mts` decides it for both the gear (`courseDetail`'s `deleteBlock`) and `remove` (again under the row lock; a staff booking holds the same row). A waiting change goes with its course, and a decision on a deleted course says the provider deleted it. "Own request" for courses = whoever created or last sent the course, or anyone who worked on the change (from `activity_log`). A course number (`/course/1012`) opens only public courses. A course never goes live under a retired category, sub-category, topic, method or level (a method: any of its learning options): retiring one with live courses filed under it is refused (`modules/admin/catalogue.mts`), and every step that puts a course live (approve, approve a change, resume, publish a shared page, a provider un-pausing) checks it (`lib/retired.mts`). Two people (or two tabs) editing one course: the editor sends the version its draft was loaded from (`seen`; the version is the later of `updated_at` and a waiting change's time, `courseVersion` in `modules/provider/courses.mts`), and every change from the editor (`provider.courses.update` / `admin.courses.updateShared`, images, send for approval, publish, withdraw, pause) refuses one over a newer version (withdrawing or rejecting a waiting change moves the version on); the editor shows its "changed somewhere else" banner for any of them (`ep.stale(error)`) ("changed somewhere else… load the latest version"); the editor's own actions return the new version (`lib/courseEditorApi.js`). A live or paused course keeps at least one image. Its pictures change at once, without review (decided 23 November 2026: the briefs ask for approval of new courses only; a course on a shared page shows the shared page's pictures, our team's); only its wording waits in `course_revisions`, and the editor says so. A pass mark is chosen in the editor as Percentage, Score or Pass or fail (`PassMarkField`) and saved as text ("70%", "26 out of 40", "Pass or fail"): a percentage up to 100%, a score not over its total, never one left without its number (`passMarkProblem`, the same in the editor and the API); one typed as other words before stays until a kind is chosen. A live online date's joining link is a Zoom, Teams or Meet address (`isMeetingLink` in `modules/provider/schedule.mts`). A provider can't add the same venue twice (same postcode and name or street), and a venue is never deleted, only archived (the brief's add, edit, switch on or off). **Cohort clashes** (`modules/provider/schedule.mts`): the same course twice at one venue, or twice live online, at overlapping times is refused (`refuseClash`); another of the provider's courses at the venue at an overlapping time is a warning, not a refusal (venues have no rooms): the date form asks `provider.cohorts.venueClash` as soon as a venue and dates are chosen and shows the words under the Venue field; saving with them shown sends `sharedVenue` (a save without it is stopped with the same words, `askSharedVenue`; on an edit only when the venue or times change); a tutor can't teach two dates at overlapping times, of any course at any provider they're on (`refuseTutorClash`, under a lock on the tutor, on create, edit and Change tutor; another provider's course is never named); a tutor is a joined member whose role can see the dates (`canTutor` in packages/permissions: not accounts or marketing; a role changed to one of those leaves their upcoming dates without a tutor), and a finished date keeps a tutor who has left. Locks go plan, course, date, tutor (`lockDate`). A venue can't be archived while its dates take bookings, and a date at an archived venue can't start taking them; a venue edit sends `seen`. A finished date is the record of what ran: it can't be edited (no Edit; `provider.cohorts.update` refuses it), only its tutor set; a running date keeps or drops the sessions it has had, but no day before today is added to it (the date form's calendar greys those days out). Saving a price plan reprices only its dates still to run, and only when its packages changed (`sameTiers`); a price is at least £1, a package can't save more than its price, and a date's was-price is at most double its price. Course editors add dates and venues. The workspace lists cancelled dates under When › Cancelled (or All cohorts), not in Upcoming or Past. A cohort's status is one pill (its dates: upcoming, in progress…) with why learners can't book it as text under it (the course in draft, in review or paused; bookings off or stopped: `CohortStatus` / `whyNotOnSale` in `ProviderCohorts.jsx`), the same in every list, the cohort page, the calendar and the Dashboard. A venue's town becomes a public town page, so it must be a UK place near its postcode, and the postcode still in use (`placeVenue` in `lib/postcode.mts`, postcodes.io; nothing is refused when it can't be reached); a town page for a town with no venue shows only for a real UK place (`ukPlace` in `lib/catalogueServer.js`), so `/courses/<page>/islamabad` is 404. A provider name is used once, whatever its case or spacing (`refuseTakenProviderName`, `lib/providerName.mts`; a rejected application doesn't hold it). Every picture upload (profile photo, provider logo, course picture) follows one rule, `prepareImage` in `apps/web/lib/images.js`: JPG, PNG or WebP (a course picture also GIF) up to 15 MB, made smaller in the browser before upload (photo 512 × 512 square; logo at most 800 px; course picture at most 2000 px), refused only below its minimum (logo 200 × 200, course picture 500 × 300). The API reads the stored file's size again (`imageSize`/`storedImageSize` in `lib/media.mts`; `addCourseImage`, `setLogo`) and deletes one that is too small or unreadable. A picture just uploaded keeps showing from the file until its saved copy has loaded (`whenLoaded`).
- Nobody decides on their own request (`notOwnRequest`). Pausing their own live course isn't one (as its provider they could pause it too), and they put back live a course they paused themselves (`pausedBy` in `modules/admin/courses.mts`); one another admin paused waits for another admin. One exception, for approvals only (a provider account, a course or a change to one; never payouts or refunds): a Full admin may decide on their own request when no other active admin has the approve switch, with a written reason; it is logged as `admin.own_request_decided` (`apps/api/src/lib/soleApprover.mts`). It switches itself off once a second approver exists.
