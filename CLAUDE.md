# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

pnpm + Turbo monorepo. Run these from the repo root:

```bash
pnpm install
pnpm dev          # api (4000) + web (3000)
pnpm dev:api      # builds packages/db, then Express + tRPC at http://localhost:4000/api/trpc
pnpm dev:web      # Next.js only, http://localhost:3000
pnpm build
pnpm typecheck    # tsc --noEmit in every package (the only static check)

pnpm db:generate  # after editing packages/db/src/schema.ts, writes SQL to packages/db/migrations (commit it)
pnpm db:migrate   # apply migrations to Supabase
pnpm db:push      # push schema directly, no migration
pnpm db:studio

pnpm admin:bootstrap <email> [--resend]   # invite the FIRST super admin (no account needed); everyone else: Admin › Team › Invite
pnpm admin:grant <email> [--preset support|finance|--super|--revoke|--reset-two-step|--list]   # change an existing login's admin role
pnpm live <command>     # run a command against the live project (LIVE_* in .env), e.g. pnpm live db:migrate
pnpm --filter @readtraining/api cleanup:media [--confirm]   # course pictures and logos uploaded but never attached (over a day old); lists them, deletes with --confirm
```

The Supabase dashboard settings every project needs (auth, SMTP, email templates, redirect URLs) are listed in `supabase/README.md`; the email templates are in `supabase/templates/`.

To run a command in one package, use `pnpm --filter @readtraining/<api|web|db> <script>`. The repo has no lint or test scripts. `playwright-core` is a devDependency of web, and QA is done by driving a browser against the dev server.

Env: copy `.env.example` to `.env` at the repo root. The API loads it through `tsx --env-file-if-exists=../../.env`, and drizzle-kit loads it through dotenv. `DATABASE_URL` is the Supabase transaction pooler (6543) and is used at runtime. `DIRECT_URL` (5432) is used for migrations. The web app reads the same root `.env` through `loadEnvConfig` in `next.config.ts` and inlines `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (the edge `proxy.js` can't read the root file).

Security headers: every page gets a Content-Security-Policy, HSTS, X-Content-Type-Options, Referrer-Policy, X-Frame-Options and Permissions-Policy (`next.config.ts` `SECURITY_HEADERS`), and the API's answers get their own (`apps/api/src/index.mts`). Before using a new outside service in the browser (a script, frame, image host or API), add its origin to the CSP there, or the browser blocks it.

Deploy: one Vercel project (`vercel.json`, Vercel Services). `/api/*` goes to the API service and everything else to the web app. Health check: `/api/trpc/health`.

## Architecture

- **packages/db**: Drizzle schema plus `createDb(url)`. It uses `prepare: false`, which the Supabase transaction pooler requires, and `max_pipeline: 0` (one query per connection at a time: the pooler hangs or mixes up answers when queries are pipelined, supabase/supavisor#1239). That setting needs `patches/postgres@3.4.9.patch` (listed in `pnpm-workspace.yaml`) so transactions still work; upgrading postgres.js means redoing or dropping the patch. It also re-exports `drizzle-orm`, so import operators like `eq` and `desc` from `@readtraining/db`. Types come from `src/index.ts`, but the runtime export is `dist/index.js`, so the package has to be built (`dev:api` does it) after schema or source changes.
- **apps/api**: ESM TypeScript with `.mts` files. Relative imports use `.mjs` extensions. The package exports `src/trpc/index.mts` (the `AppRouter` type). `src/trpc/trpc.mts` defines `createTRPCRouter`, `publicProcedure` and `protectedProcedure` (superjson transformer, zod errors flattened into `data.zodError`). The context (`src/trpc/context.mts`) holds `db`, the `user` from a verified Supabase access token (`Authorization: Bearer <access_token>`, checked by `verifyAccessToken` in `src/lib/supabase.mts`; none or an invalid one means signed out) and `loadIdentity()` (whether the session is still live, `isSessionLive`, and the person's roles, `loadActor` in `src/lib/actor.mts`, asked once per request). Feature routers go in `src/modules/<name>/<name>.router.mts` and are mounted in `src/trpc/router.mts`. Mounted routers: `health`, `me`, `organisations`, `catalogue`, `content`, `admin` (which holds the admin's own sub-routers) and `provider` (the provider workspace: `courses`, `cohorts`, `venues`, `profile`; every procedure is `orgProcedure(...)` on the caller's role). `src/lib/supabase.mts` is a server-only admin client (null when env is missing), and DB queries go through Drizzle.
- **apps/web**: Next.js 16 App Router, React 19. It is mostly `.jsx`; TS is used only for the tRPC client. It imports only the `AppRouter` **type** from `@readtraining/api` (`lib/trpc/react.ts`), so API code never enters the bundle. `app/layout.jsx` is a server component with the site-wide metadata; `app/Providers.jsx` (client) holds `TRPCProvider`, the cart `Context` (`context/Context.js`, persisted to localStorage under `rt-cart`) and the AOS animations. `app/sitemap.js`, `app/robots.js`, `app/error.jsx` and `app/global-error.jsx` exist. Path alias `@/*` → `apps/web/*`.

### Accounts, provider workspace and admin

- **Auth is Supabase Auth in the web app**, not the API: `lib/supabase/{client,server}.js`, `lib/auth/*`, and `proxy.js` (Next 16's name for middleware). The proxy refreshes the session cookie, sends signed-out visitors of `/account`, `/business` and `/provider` to `/login?next=…`, and sends signed-in visitors away from `/login` and `/signup`. It also sends `/courses?subject=<one subject>` to that subject's page `/courses/<subject>` (307, so a subject retired later isn't kept by browsers; other filters kept), so each subject has one address; links use the page form. Pages still check the session themselves. With no Supabase env, protected areas redirect to login and the rest of the site works.
- **Closing an account** is a request, not a self-service delete: Account settings › Close your account (`me.requestClosure`, current password unless they sign in with Google; `me.withdrawClosure`) saves it in `account_closure_requests` (API only, no foreign key, so the record outlives the account; one open request per person), logs `account.closure_requested`, emails the person (`closure-received`) and every admin with the `suspend` switch (`admin-closure-request`, `notifyAdmins` in `lib/notify.mts`). The learner's admin page shows the request and its one-month deadline (UK GDPR); staff close the account.
- `/account` (learner), `/business` (business account) and `/provider/*` (provider workspace, modelled on Hurak's provider side; `lib/providerWorkspace.js`) are mostly front end only: their records are demo data in `data/` plus localStorage. Their real parts are the account's settings, the organisations, a provider's account status (a one-line status bar on every workspace page, `ProviderAccountStatus`; the Account review page `/provider/review` with our team's message, "send for review" and the history from `activity_log`; the dashboard's getting-set-up checklist, `ProviderChecklist`; the name can change only while the account is under review) and, since Milestone 2, the provider's courses (editor, images, approval, changes to a live course waiting in `course_revisions`), dates (`cohorts`), venues, profile, logo and terms, all through the API `provider.*` (images and logos in the public `course-media` bucket, uploaded through signed addresses). The browser hides buttons with the shared table (`lib/providerAccess.js`). Orders, learners, bookings, reviews, leads, price plans and the sample cohorts they link to are still demo (`lib/providerWorkspace.js`); a cohort page with a non-uuid id is a sample one. The Team page and the VAT, emails, Q&A and integrations settings would only save in the browser, so they sit behind "coming soon" switches in `lib/forms.js` (`providerTeam`, `providerSettings`), as does the Business account's Team page (`businessTeam`), and never show a made-up result. `/admin/*` (operator panel) is part real, part demo (Part B of `docs/milestone-1-and-admin.md`):
  - **Real (API `admin.*`, `content.*`):** admin team, activity log, learners, providers and approvals (decisions email the owner), commission, catalogue settings (categories, methods, levels), site content, emails (every automated email's words: `apps/api/src/emails/templates.mts`, saved as content keys `email:<template>`, never sent to the website; the "something is waiting" emails (a provider application or course received, a new business account, an admin's access changed, and the alerts to every admin with the `approve` switch) go through `apps/api/src/lib/notify.mts`, after the change is saved, and never block it), coupons (`coupons` table), course approvals and the catalogue's courses (`admin.courses` in `modules/admin/courses.mts`: new courses and changes to live courses, decisions emailed to the provider's owner, and the shared course pages staff write and publish in the provider course editor run with `scope="admin"` through `lib/courseEditorApi.js`), money (orders, refunds, disputes, payouts and the append-only `ledger_entries`, in `modules/admin/money.mts` and `payouts.mts`; the maths is `apps/api/src/lib/money.mts`: fee off the gross, commission on the net, amounts in pence; no payment provider yet, so orders come from staff bookings and refunds/payouts are recorded, not paid; `pnpm --filter @readtraining/api seed:money` adds made-up records to a dev database, never live) and platform settings (the search-engine words, content key `seo`, and which outside services' environment variables are set; their values never leave the server). ## Database rules (Supabase + Drizzle)

The schema is built on a development Supabase project and replayed later on the client's test and live projects, so the migrations must rebuild everything from an empty database.

- Every change goes `packages/db/src/schema.ts` → `pnpm db:generate` → `pnpm db:migrate`. Never change tables in the Supabase dashboard, and never use `db:push` on a shared or client database.
- Never edit a migration that has already run. A fix is always a new migration.
- Supabase-specific SQL (triggers on `auth.users`, RLS policies, grants, storage buckets, extensions) goes in custom migrations (`drizzle-kit generate --custom --name <name>`), not in the dashboard.
- No demo or test data in migrations. Seed data goes in a separate script that never runs on live.
- Every public table calls `.enableRLS()`. Drizzle connects as `postgres` and skips RLS, but the Data API is reachable with the public key, so RLS is what protects it. Policies are owner-only reads using `(select auth.uid())`; writes go through the API. A table the browser doesn't read (all but `profiles`, `organisations`, `organisation_members`) has no grants for `anon` or `authenticated` and an explicit restrictive "<table>: API only" policy (migration 0025); new tables start with no grants. So a new API-only table needs that policy in a custom migration (or the Security Advisor flags it), and a table the browser must read needs `grant select ... to authenticated` plus an owner-only policy.
- Database functions are `security definer` with `set search_path = ''`.
- Append-only tables (`activity_log`, `site_content_versions`, `ledger_entries`) have no foreign keys, so removing an account never has to change a row, and a trigger blocks update, delete and truncate.
- An action that checks a row's state and then changes it locks the row first: inside the transaction, `select ... for update`, check again, then write (`lockCourse`/`lockStatus` in `modules/provider/courses.mts`, `lockTeam` in `modules/admin/team.mts`). Emails go after the commit. So two clicks or two people at the same moment act once, and the second is told it has been done.
- Run the Supabase security and performance advisors after each migration. Before moving to the client, apply all migrations to a fresh, empty project first.

## Sign-in and security rules

- **Bots and abuse (four layers).** (1) The Vercel Firewall (dashboard, free Hobby plan): known scanner paths are denied and
  each IP gets 300 `/api/` requests a minute. (2) Cloudflare Turnstile: `apps/web/lib/humanCheck.js` gets a fresh one-use token
  on sign-up, sign-in, forgot password, the confirmation resend and both admin sign-ins (passed to Supabase as `captchaToken`;
  Supabase's CAPTCHA protection checks it), and on every public form (`sendForm` adds `humanCheck`; the API's
  `publicFormProcedure` checks it with `lib/humanCheck.mts`, so every public form endpoint MUST be built on it). (3) The API:
  `lib/rateLimit.mts` (Upstash Redis via `KV_REST_API_*`, or memory without them) caps each IP at 300 requests a minute and,
  through `limit(ctx, name)`, provider applications, business accounts, admin invites and picture-upload links per person; a
  request body over 100 KB is refused (413). (4) The `course-media` bucket accepts only images up to 2 MB. Production needs
  `NEXT_PUBLIC_TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY`; preview and development copies use Cloudflare's test keys.
  Supabase's CAPTCHA switch is turned on only after the code that sends the token is live (otherwise nobody can sign in).

- On the server, verify the user with `supabase.auth.getClaims()` (it checks the JWT signature locally), never `getSession()`. Use `getUser()` only when fresh user data is needed.
- Only the publishable key reaches the browser. The service-role key stays in the API, for admin tasks only.
- Email links (confirm, reset) use the token-hash flow at `/auth/confirm`. Google/Facebook use `/auth/callback` (PKCE code exchange).
- A `next` redirect is accepted only if it starts with `/` and not `//`.
- Forgot password always shows the same message, so it never reveals whether an email exists.
- Changing email or password requires the current password.
- The tRPC client sends `Authorization: Bearer <access_token>`, and the API verifies it with `getClaims(token)` (issuer, audience and role checked). A protected call also needs the session to still exist and the account not to be banned or deleted (`isSessionLive`), since a token stays valid until it expires.

## Identities, roles and permissions

One login can hold several identities:
- Student: every account. A learner is at least 16 (`MIN_AGE` in `modules/me/me.router.mts` and `AccountProfile.jsx`; the work courses here start at 16).
- Business and Provider: an `organisations` row with `organisation_members`.
- Admin: an `admin_users` row, signed in at `/admin/login`, with no public sign-up. Admins are invited (`apps/api/src/lib/adminInvite.mts`): someone without an account gets a staff-only login (`admin_only`, kept out of Learners) and an email to `/admin/welcome` to set their name and password; access starts only when the invite is accepted.

Roles:
- Provider roles follow Hurak: owner, admin, tutor, course_editor, support, sales, accounts, marketing, assistant.
- Business roles: owner, member.
- Admins have one role with permission switches and presets (Full, Support, Finance). Full requires two-step sign-in (`needsTwoStep`; a Full admin without an authenticator sets one up at the admin login). A test copy can waive it for a client review with `ADMIN_TWO_STEP_OPTIONAL=1`, which live ignores (`apps/api/src/lib/actor.mts`).

How permissions are checked:
- One shared `can(actor, action, target)` table, used by both the API and the web server code.
- It is enforced on the server: in tRPC procedures (signed in, organisation member, admin permission) and in the server layouts for `/provider`, `/business` and `/admin`. The browser uses it only to hide buttons.
- Provider staff only ever see their own organisation's data. Within it, the organisation's private details (its mobile, commission, terms acceptance and our team's status note and messages) are for the owner and admins only: the database policy "organisations: read where owner or admin", active members only (migration 0028) and the API (`PRIVATE_ROLES` in `modules/provider/profile.mts`, used by `profile.review` and `organisations.openWorkspace`); other members see the account's status without the note.
- Every allowed change and every refused attempt is written to `activity_log`, which is append-only (no update or delete). A change and its log line are written in one transaction. The IP recorded (`ctx.ip`, and the rate limits: `clientIp` in `lib/clientIp.mts`) trusts forwarded headers only on Vercel (or with `TRUST_PROXY=1`, then only the last x-forwarded-for entry); elsewhere it is the connection's address.
- Course review: a provider's change to a course waiting for approval (words or pictures) takes it out of review, back to a draft (`leaveReview` in `modules/provider/courses.mts`), so admins never approve an unseen version; approval re-checks `missing()`; a change to a live course is decided on the version the admin saw (`seen`, the change's time) and one edited since is refused. "Own request" for courses = whoever created or last sent the course, or anyone who worked on the change (from `activity_log`). A course number (`/course/1012`) opens only public courses. A course never goes live under a retired category, sub-category, topic, method or level: retiring one with live courses filed under it is refused (`modules/admin/catalogue.mts`), and every step that puts a course live (approve, approve a change, resume, publish a shared page, a provider un-pausing) checks it (`lib/retired.mts`). Two people (or two tabs) editing one course: the editor sends the version its draft was loaded from (`seen`; the version is the later of `updated_at` and a waiting change's time, `courseVersion` in `modules/provider/courses.mts`), and every change from the editor (`provider.courses.update` / `admin.courses.updateShared`, images, send for approval, publish, withdraw, pause) refuses one over a newer version (withdrawing or rejecting a waiting change moves the version on); the editor shows its "changed somewhere else" banner for any of them (`ep.stale(error)`) ("changed somewhere else… load the latest version"); the editor's own actions return the new version (`lib/courseEditorApi.js`). A live or paused course keeps at least one image. A pass mark is a percentage up to 100%, a score not over its total, or words (`passMarkProblem`). A live online date's joining link is a Zoom, Teams or Meet address (`isMeetingLink` in `modules/provider/schedule.mts`). A provider can't add the same venue twice (same postcode and name or street), and a venue any date has used is archived, not deleted. A venue's town becomes a public town page, so it must be a UK place near its postcode, and the postcode still in use (`placeVenue` in `lib/postcode.mts`, postcodes.io; nothing is refused when it can't be reached); a town page for a town with no venue shows only for a real UK place (`ukPlace` in `lib/catalogueServer.js`), so `/courses/<page>/islamabad` is 404. A provider name is used once, whatever its case or spacing (`refuseTakenProviderName`, `lib/providerName.mts`; a rejected application doesn't hold it). Every picture upload (profile photo, provider logo, course picture) follows one rule, `prepareImage` in `apps/web/lib/images.js`: JPG, PNG or WebP (a course picture also GIF) up to 15 MB, made smaller in the browser before upload (photo 512 × 512 square; logo at most 800 px; course picture at most 2000 px), refused only below its minimum (logo 200 × 200, course picture 500 × 300). The API reads the stored file's size again (`imageSize`/`storedImageSize` in `lib/media.mts`; `addCourseImage`, `setLogo`) and deletes one that is too small or unreadable. A picture just uploaded keeps showing from the file until its saved copy has loaded (`whenLoaded`).
- Nobody decides on their own request (`notOwnRequest`). One exception, for approvals only (a provider account, a course or a change to one; never payouts or refunds): a Full admin may decide on their own request when no other active admin has the approve switch, with a written reason; it is logged as `admin.own_request_decided` (`apps/api/src/lib/soleApprover.mts`). It switches itself off once a second approver exists.
